# Real-Hi-Res in Rust

This folder holds the Rust port of Real-Hi-Res: the desktop app (since 2.0 a music player with the quality checker inside) and the command-line tool. It judges every file exactly as the Python version in `realhires/` does, and it shares that version's settings file and saved results. The user-facing description is in the main [README](../README.md#rust-version-preview); this file is for building and working on the code.

## Building and testing

You need Rust 1.95 or newer (on Linux also the ALSA headers, `libasound2-dev` on Debian and Ubuntu or `alsa-lib-devel` on Fedora and AlmaLinux, for the player's sound output) and FFmpeg (`ffmpeg` and `ffprobe` on the `PATH`, or in an `ffmpeg` folder next to the executable, or in the folder `$REALHIRES_FFMPEG_DIR` names). Build the optimised programs with:

```bash
cargo build --release
```

Run the tests (the core's unit tests and the desktop app's tests, which drive the whole app without a screen or a sound device and need FFmpeg) with:

```bash
cargo test
```

The comparison with the Python version is a pytest in the main repository, because it reuses the synthetic test library of the Python tests. Run it from the repository root after the release build:

```bash
python3 -m pytest -q tests/test_rust_parity.py
```

## Layout

The workspace has one library and the programs built on it.

| Crate | Contents |
| --- | --- |
| `crates/core` (library `realhires`) | The detection pipeline and everything around it, one module per Python module: `probe` (ffprobe metadata, tags, the PCM stream from ffmpeg), `analysis` (Welch spectrum, bit-depth histogram, value grid, every spectral rule), `verdict` (`FileResult`, the judging rules, `analyze_file`), `settings`, `store` (the shared SQLite results), `fix`, `report` (table, JSON, CSV, SVG), `imaging` (spectrogram PNG), `eta`, `library` (album and artist groups), `covers` and `lyrics` (synced lyrics from LRCLIB: the polite client over `ureq` with rustls and ring, the system's certificates or else the bundled Mozilla roots, the proxy from `$https_proxy`/`$no_proxy`, and the same matching rules and files as `realhires/lyrics.py`). Three helper modules have no Python counterpart: `dsp` holds the NumPy functions the rules use, with NumPy's exact semantics (median, linear percentile, `convolve(mode="same")`, `polyfit`, window functions); `pyfmt` formats numbers exactly as Python does (`{:g}`, `{:%}`, `repr(float)`, `round()`), so every reason is the same text; `json` reads and writes Python's JSON dialect (`NaN`, `Infinity`, Python's float notation), which the saved results and the settings key depend on. Version 2.0 added the player's core, again one module per Python module: `eq` (the graphic and parametric equalizer's biquads, response curve and headroom, and `EqProcessor`, which filters the samples in the audio callback), `playqueue` (the shuffle and repeat modes, with SplitMix64 so a seed gives Python's order), `playerstate` (`player.json`), `musiclib` (`library.sqlite`, the tag index of the library folders, its groupings and the play history), `embed` (lyrics inside FLAC and MP3 files), `stats` (Your Stats) and `themes` (built-in and user themes, `themes.json`); `tests/python_*.json`, written by `rust/tools/gen_player_vectors.py`, hold Python's answers, which `tests/player_additions.rs` and the unit tests compare. `paths` matches `os.path.abspath` so both versions key saved results by the same path string. `pyunicode` holds Python's `str.isalnum()`, `str.isspace()` and `str.casefold()` tables, so lyrics names are compared exactly as in Python; it is generated by `rust/tools/gen_pyunicode.py`. Version 2.1 added `i18n` (the language setting: `tr!()`, `tr_name()`, `tr_text()` with the patterns of the shared catalog `realhires/assets/lang/ja.json`, included at build time; `tests/python_i18n.json` and `tests/i18n_vectors.rs` check it against Python) and `musicbrainz` (song information from MusicBrainz: the one-request-per-second client over the lyrics module's `ureq` transport, release and recording searches, release lookups, matching songs to tracks, the changes to write, the automatic lookup and its log in `library.sqlite`; `tests/python_musicbrainz.json` and `tests/musicbrainz_vectors.rs` check it against Python, also on real FLAC files). |
| `crates/cli` (program `realhires`) | The command-line tool, with the options of `realhires/cli.py`. Files are analysed by worker threads, and the results are printed and saved in file order by the main thread. |
| `crates/gui` (program `universal-music-player`) | The desktop app, built with egui/eframe (OpenGL through glow), rfd for the system's file dialogs, cpal for the sound output (WASAPI, CoreAudio, ALSA) and fontique to list the installed fonts. Since 2.0 the window is the music player of `docs/player-spec.md`: `player.rs` holds its state and logic (library index, play queue, playback events, likes, the saved state), the sidebar, the playback bar with the LCD and the Up Next panel; `pages.rs` the pages (album cards, the album page, song tables, the grouped pages, search, Now Playing with the synced lyrics, and the Settings page with the theme editor); `library_pages.rs` the Library start page, Folders, Playlists, Recently Played and Your Stats; `eqwin.rs` the Equalizer and Playback info windows; `audio.rs` the engine (FFmpeg decodes to 32-bit float stereo at the output rate into a two-second buffer, the cpal callback runs the EQ and the volume, the next song is decoded into the same buffer for gapless playback, and `REALHIRES_AUDIO_BACKEND=null` plays into a timer for tests and machines without sound); `look.rs` the fonts (SF Pro from the system on macOS, the bundled Inter elsewhere, or the family chosen in Settings) and the light and dark palettes; and `icons.rs` the vector icons. The 1.x window lives on as the Quality check page: `app.rs` holds it and its state (sources, the file list and its rows, filters, search, find, the album and artist cards, the dashboard and the status bar), `dialogs.rs` the summary chart, the Settings window (built from `Settings::field_info()`), the Fix window, the pop-up after fixing and the confirmations, `lyrics.rs` the Download synced lyrics window and the dashboard's Lyrics tab, `plots.rs` the spectrogram and spectrum views, `work.rs` the background threads (listing, saved-result lookups, scanning, graphs, covers, fixing, lyrics), which post messages to the UI thread, and the on-disk plot cache, and `style.rs` the verdict colours and helpers. Since 2.1 every text goes through `tr!()` (the language changes at once), and `mbwin.rs` is the MusicBrainz window (Get info from MusicBrainz… and Get album info from MusicBrainz…). Its tests (`app::tests` for the Quality check page, `player::tests` for the player, `audio::tests` for the engine) run headlessly with `egui::Context::run_ui` and the null sound output. |

## Keeping it equal to the Python version

Every change to the detection rules, the reasons and summaries, the settings, the saved-results format, the CLI options, Fix or the desktop app's behaviour must be made here too, in the same commit, and `tests/test_rust_parity.py` must pass. The version in `Cargo.toml` (`[workspace.package] version`) is kept equal to `realhires.__version__`, which `test_rust_port_has_the_same_version` checks, because both versions write it into the saved results they share. `verdict::DETECTOR_VERSION` must equal the Python `DETECTOR_VERSION` for the same reason.

## Packages

Since version 1.12.0 every release carries the Rust version as `UniversalMusicPlayer-Rust-<version>-<platform>` packages with FFmpeg bundled. They are built by the `rust-*` jobs of `.github/workflows/build.yml` with `packaging/rust_build.sh`, which also runs the tests above and the comparison with the Python version, checks the binaries with `packaging/check_compat.py`, and smoke-tests the packaged command-line tool. On Windows, `windows_resources.rs` gives both programs an icon and version information, and `.cargo/config.toml` links the C runtime statically.
